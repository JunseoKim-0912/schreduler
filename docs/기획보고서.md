## 1. 프로젝트 개요

이 앱은 단순 일정 기록용 캘린더가 아니라, **"계획을 지키게 강제하는" 스케쥴 관리 시스템**이다. 세 가지 축으로 기존 캘린더 앱과 차별화된다.

1. **자연어 인터페이스** — 사용자가 대화하듯 일정을 말하면 LLM이 부족한 정보를 되물어 채운다.
2. **엄격한 실행 관리 (Enforcement)** — 일정 시작/종료 시점에 알림을 보내고, 완료 체크를 직접 하게 만들며, 어겼을 경우 사유를 기록해 피드백에 활용한다.
3. **정서적 완충 장치 + 게이미피케이션** — 가상 캐릭터와의 대화로 부담을 낮추고, 규칙적인 생활을 포인트로 보상한다.

**아키텍처 원칙:** 백엔드(캘린더, LLM 연동, 알림 스케쥴링, DB)는 전부 Python(FastAPI)으로 구현한다. 클라이언트(모바일 앱 UI)는 Flutter 또는 React Native로 별도 구현하고 Python 백엔드와 REST/WebSocket API로 통신한다. **한국어/영어 두 언어를 모두 지원**한다 (FR-11).

## 2. 핵심 기능 명세 (Functional Requirements)

### FR-1. 캘린더 코어

이벤트의 기본 속성(날짜, 시작 시각, 지속 시간, 제목/설명), 단발성/반복 이벤트 지원, 월/주/일 뷰. (변경 없음)

**✅ v3.4 추가 — 마감일(Deadline) 이벤트 타입:** 과제 마감일처럼 "시작 시각"이 의미 없고 "언제까지"만 있는 항목을 위해, `Event.event_type` 필드(`scheduled` / `deadline`)를 추가한다. `scheduled`(기본값)는 기존처럼 `start_time`/`end_time`이 모두 필요한 시간대 이벤트이고, `deadline`은 `start_time`이 `null`이며 `end_time` 하나만 "마감 일시"로 쓴다. 새 테이블을 만들지 않고 기존 `Event`를 재사용하므로, 반복(`recurrence_rule`), 중요도, Child 이벤트(FR-5), 미준수 사유(FR-6), 포인트(FR-10) 로직을 그대로 물려받는다 (예: "매주 금요일까지 제출하는 과제"도 반복 마감일로 표현 가능). FR-4 알림만 `event_type`에 따라 분기한다 (상세: FR-4 참고).

**✅ v3.5 추가 — Task List (할 일 목록) 편의 API:** 사용자가 마감일 이벤트들을 "할 일 목록" 형태로 따로 조회/관리하고 싶어해서, 별도 테이블 없이 `event_type="deadline"`인 `Event`/`EventInstance`를 대상으로 하는 편의 API(`/tasks`)를 추가한다. Task는 개념적으로 deadline 이벤트와 동일한 객체이므로 알림·에스컬레이션·미준수 리포트·포인트 적립이 전부 그대로 적용된다 — "가벼운 체크리스트"가 아니라 "마감일 이벤트를 목록 뷰로 보여주는 것"에 가깝다. `GET /tasks`(마감일 오름차순, 완료 여부·overdue 여부 포함), `POST /tasks`(deadline 이벤트 생성 축약형), `PUT /tasks/{event_instance_id}/complete`(완료 처리 축약형) 세 엔드포인트로 구성한다.

### FR-2. 자연어 일정 관리 — v4 도구 기반 일정 어시스턴트

사용자가 자연어로 일정을 추가·수정·삭제하고, 반복 기간을 만들거나 바꾼다. **중요 기간(Important Date Range)** 개념으로 "학기", "인턴십" 등 임의의 기간을 등록해두고 반복 종료 기준으로 재사용한다 (v2에서 확정).

**원칙: LLM은 추론하고 제안한다. 백엔드는 검증하고 저장한다. 사용자는 확인한다.** 상세 설계는 [docs/assistant_design.md](assistant_design.md).

- **되묻기보다 추론:** 어시스턴트는 빠진 값(종료 시각, 중요도, 반복 기간, 오전/오후, 새 장소의 이동 시간 등)을 상식으로 채운 초안을 만들고, 추론한 항목에는 "추정" 표시를 붙인다. 무엇을 할지 전혀 알 수 없거나 삭제 대상 후보가 여러 개인데 고를 근거가 없을 때만 되묻는다.
- **도구:** 기존 일정 찾기(`search_events`), 생성·수정·삭제 초안, 반복 기간 초안, 채팅 승인(`confirm_pending`). DB에 쓰는 도구는 승인뿐이다. 수정·삭제 대상 ID는 이번 대화에서 검색으로 찾은 것만 받는다(환각한 ID로 엉뚱한 일정을 지우지 않게).
- **백엔드 검증:** 모든 초안은 공용 규칙(`draft_rules`)으로 검증·정규화한다 — RRULE 조립(INTERVAL 포함), 첫 회차·미리보기 3회차, 시간 표시("오전 11:00 – 오후 1:00 (2시간)", "(다음 날)"). 자정 넘김, 12시간 초과, 지난 날짜, 반복 시작일과 요일 불일치, 사용 중인 기간 삭제, 여러 개 한꺼번에 변경은 카드에 경고로 보여준다.
- **확인 후 실행:** 초안은 확인 카드로 보여주고, [만들기] 버튼이나 "좋아" 같은 채팅 승인으로만 저장한다. 같은 턴에 만든 초안을 스스로 승인할 수 없다. 새 제안은 이전 제안을 대체하고, 제안은 30분 뒤 만료된다. 여러 초안(예: 새 기간 + 그 기간을 쓰는 일정)은 한 트랜잭션으로 실행한다.
- **되돌리기(Undo):** 모든 실행은 `ActionHistory`에 변경 전 스냅샷과 함께 기록한다(v3.6). 되돌리면 원래 ID·회차·Child 이벤트·알림 잡을 복원하고, 지난 날짜가 영향을 받았으면 포인트 원장도 다시 계산한다. 일정과 함께 만든 기간·장소는 다른 일정이 쓰지 않으면 같이 지운다.
- **반복 일정:** 반복의 기준일(dtstart)은 격주 리듬의 기준으로만 쓰고(사용자가 말한 시작일, 없으면 기간 시작일 이후 첫 해당 요일), 실제 회차는 오늘 이후만 만든다. 기간을 늘리거나 줄여도 리듬이 유지되고, 줄이면 범위 밖 대기 회차만 취소한다(완료·놓침 기록은 그대로).
- **장소:** 일정에 장소를 넣고·바꾸고·빼면 이동 하위 일정(FR-5)을 만들거나 다시 맞추고, 장소를 빼면 앞으로 남은 이동 회차만 취소한다.
- **대화 상태:** 대화·제안·토큰은 DB(`assistant_sessions` 등)에 둔다. 탭을 옮기거나 새로고침해도 오늘 대화를 이어 보여준다.
- **API·모델:** Responses API + 추론(`ASSISTANT_MODEL` 기본 `gpt-5.6-luna`, `ASSISTANT_REASONING_EFFORT` 기본 `medium`). 평가 세트(`tests/assistant_eval`)로 모델·추론 강도를 고르고, 옛 방식과 비용을 비교했다(같은 비용, 더 높은 정확도 — assistant_design.md §11.9).

**v3–v3.8 슬롯필링 (v4에서 대체됨):** v3~v3.8의 FR-2는 LLM이 정해진 슬롯(제목·요일·시각·중요도·기간)을 채우고 부족한 것을 되묻는 방식이었다(`POST /events/parse`). 의도 분류(v3.6), 대화 중 반복 기간 관리(v3.7), 반복 간격·장소 수정·마감 입력·대화 상태 초기화(v3.8)를 차례로 붙였지만, 규칙을 하나씩 덧붙이는 구조에서 격주 무시, 오전/오후 오해, 대화 상태 누수 같은 버그가 반복돼 v4에서 어시스턴트로 교체하고 코드를 제거했다(태그 `before-remove-nl-parse`). 되돌리기·기간 회차 맞추기·장소 이동 일정·제목 매칭 규칙은 v4에 그대로 이어졌다.

### FR-3. 중요도(Importance) 체계

[3. 중요도 체계](#3-중요도-importance-체계) 참고. (변경 없음)

### FR-4. 출석/수행 확인 알림 (Strict Enforcement)

이벤트 시작/종료 시점 앱 푸시 알림(FCM), 사용자 동의 시 GPS 자동 확인 병행. 완료 체크는 사용자가 직접. (v2에서 확정, 변경 없음)

**✅ v3.4 추가 — 마감일 이벤트 알림 분기:** `Event.event_type`이 `deadline`인 경우 시작 알림은 생성하지 않는다. 대신 (1) 마감(`end_time`) 1일 전 리마인더 알림, (2) 마감 시각의 완료 여부 확인 알림, 이렇게 두 개만 생성한다. `scheduled` 타입 이벤트는 기존처럼 시작/종료 알림 두 개를 그대로 유지한다.

#### FR-4-1. 통합 에스컬레이션 정책

개별 이벤트 무응답과 앱 전체 미접속에 동일한 규칙 적용: 1주(텔레그램 opt-in 알림) → 2주(모든 알림 중단) → 3주(최종 메시지 후 완전 중단), 응답 시 즉시 리셋. (v2에서 확정, 변경 없음)

### FR-5. Child 이벤트

부모 이벤트의 이동/준비 시간을 하위 이벤트로 자동 생성, 중요도 상속. 초기엔 사용자가 장소별 이동시간을 수동 등록. (v2에서 확정, 변경 없음)

### FR-6. 미준수 시 사유 조사 + 피드백 DB

카테고리 선택(필수) + 자유 텍스트(선택, ≤150자)의 2단계 입력. 카테고리: `overslept`, `fatigue`, `priority_shift`, `schedule_conflict`, `forgot`, `transit_issue`, `other`.

**✅ v3 추가 — LLM 우회 UI 숏컷:** 사용자가 카테고리 버튼(`overslept`, `fatigue` 등)만 누르고 끝내면 **LLM을 전혀 호출하지 않고 바로 `ComplianceReport` 테이블에 저장**한다. LLM 호출(사유 분석·페르소나의 공감/피드백 반응 생성)은 사용자가 `other`를 선택했거나, 카테고리 선택 후 자유 텍스트를 추가로 입력했을 때만 트리거된다. 즉 "버튼 클릭만으로 끝나는 대다수 케이스"는 인퍼런스 비용이 0이다.

### FR-7. 실제 수면 시간 체크

기상 직후 어제 취침/오늘 기상 시각 질문, 실제 수면 패턴 기록. (변경 없음)

### FR-8. 매일 밤 9시 하루 요약 체크인

오후 9시 체크인으로 "실제 하루" 캘린더를 계획 캘린더와 별도 레이어로 저장.

**✅ v3 추가 — 컨텍스트 동적 로딩:** 체크인 시점에 하루 전체 `EventInstance` 로그를 통째로 LLM에 넘기지 않는다. 백엔드가 미리 상태를 판별해:
- **완료(`done`) 이벤트:** 개수만 요약 (예: "오늘 계획한 6개 중 5개 완료").
- **미완료(`missed`) 이벤트:** 제목·시간·[FR-6]에서 기록된 미준수 사유까지 상세히 프롬프트에 포함.

이렇게 하면 LLM이 굳이 다 알 필요 없는 "잘 지킨 일정"에 토큰을 쓰지 않고, 대화가 필요한 "놓친 일정"에만 컨텍스트를 집중시킬 수 있다.

### FR-9. 가상 AI 캐릭터를 통한 대화형 인터페이스 (플래그십 기능)

사전 정의된 페르소나 3~5개(초안 4종: 코치 강한결/다정한 유리/선배 정우/말랑이), JSON으로 DB 저장 후 시스템 프롬프트로 주입. (v2에서 확정)

**✅ v3 추가 — 프롬프트 캐싱:** 페르소나 설정(`tone_description`, `sample_lines` 등 고정된 부분)과 사용자의 중요 기간(Important Date Range) 목록처럼 자주 재사용되지만 자주 바뀌지 않는 컨텍스트는 **API 프롬프트 캐싱**(Claude/OpenAI가 지원하는 기능)을 이용해 캐시에 올려둔다. 매 호출마다 이 고정 정보를 새로 입력 토큰으로 계산하지 않아도 되므로, 대화가 잦은 페르소나 인터랙션에서 입력 토큰 비용을 크게 절감할 수 있다. (설계 시 유의점: 캐시는 "완전히 동일한 프리픽스"일 때 효과가 크므로, 페르소나 JSON과 중요 기간 목록처럼 자주 안 변하는 내용을 프롬프트 앞부분에 고정 배치하고, 매번 달라지는 사용자 발화·이벤트 정보는 뒤쪽에 붙이는 구조로 설계.)

**✅ v3 추가 — 다국어 페르소나 (FR-11 연동):** 각 페르소나의 `display_name`, `tone_description`, `sample_lines`는 언어별로 분리 저장한다.

```json
{
  "persona_id": "coach",
  "display_name": { "ko": "코치 강한결", "en": "Coach Kang" },
  "tone_description": {
    "ko": "직설적이고 절도 있는 반말, 강한 동기부여형",
    "en": "Blunt, disciplined, highly motivational tone"
  },
  "sample_lines": {
    "event_start_check": {
      "ko": "지금 시간이면 벌써 가 있어야죠! {event_title} 가셨어요?",
      "en": "You should already be there! Did you make it to {event_title}?"
    }
  }
}
```

LLM 호출 시 `User.preferred_language` 값을 시스템 프롬프트에 명시해 해당 언어로만 응답하도록 강제한다.

**✅ v3.2 추가 — description 기반으로 스키마 단순화 (개발자가 하드코딩 없이 페르소나 생성 가능):** 위 예시처럼 `tone_description`/`sample_lines`를 세부 필드로 쪼개는 대신, **자유 텍스트 `description` 필드 하나**에 페르소나의 성격·말투·톤을 한 문단으로 서술하고, 이를 대화 시 시스템 프롬프트에 그대로 삽입하는 방식으로 단순화한다 (언어별로 필요하면 `description`을 언어별로 하나씩 저장). 이 방식의 장점: (1) 개발자가 Python 코드를 건드리지 않고 DB에 row 하나(이름 + 설명 문장)만 추가해도 새 페르소나가 즉시 동작한다. (2) Persona CRUD API(`POST/GET/PUT/DELETE /personas`, 9주차 구현)를 그대로 관리자 화면이나 프론트엔드 폼에 연결하면, 비개발자도 "이름 + 설명" 입력만으로 페르소나를 만들 수 있어 향후 확장성이 좋다.

**✅ v3.3 추가 — 예시 대사 + 배경 스토리 (few-shot으로 캐릭터 일관성 강화):** 플래그십 기능인 만큼, `description` 한 문단만으로는 대화가 여러 턴 이어질 때 캐릭터 톤이 흔들릴 수 있다. 이를 보완하기 위해 두 개의 선택적 필드를 추가한다.
- `example_lines` (언어별): `{ "situation": "...", "line": "..." }` 형태의 대표 상황별 실제 대사 3~5개 (예: "사용자가 지각했을 때", "목표를 달성했을 때", "반복해서 놓쳤을 때"). LLM 프롬프트 엔지니어링에서 말하는 few-shot 예시 역할을 해서, description만 줄 때보다 캐릭터의 말투가 대화 내내 훨씬 안정적으로 유지된다.
- `backstory` (언어별): 캐릭터가 왜 그런 성격을 갖게 됐는지 설명하는 짧은 배경 이야기 한 문단. 캐릭터의 "왜"까지 LLM에 제공해 반응의 일관성과 개연성을 높인다.

두 필드 모두 `description`과 함께 시스템 프롬프트 앞부분(자주 안 바뀌는 부분)에 배치되어, 9주차 Day 3의 프롬프트 캐싱 대상에 그대로 포함된다.

```json
{
  "name": "rordon",
  "display_name": { "ko": "로든 갬지", "en": "Rordon Gamsay" },
  "description": { "ko": "...", "en": "..." },
  "example_lines": {
    "ko": [
      { "situation": "사용자가 지각했을 때", "line": "지각하는 너를 기다리자니 차라리 남극에서 웰던 스테이크를 구워먹는 게 더 빠르겠다." }
    ],
    "en": [
      { "situation": "User is late", "line": "It would be faster to eat a well-done steak at the South Pole than to wait for you here." }
    ]
  },
  "backstory": {
    "ko": "한때 미슐랭 별을 노리던 주방에서 완벽을 요구받으며 일했다...",
    "en": "..."
  }
}
```

**✅ v3.8 추가 — 의미 없는 입력 LLM 우회, 페르소나별 대화 유지:**

- **의미 없는 입력 LLM 우회:** 키보드 난타, 같은 글자 반복, 기호만, 1000자 초과, 알려진 프롬프트 인젝션은 규칙으로 걸러 LLM 없이 페르소나의 `fallback_lines`(언어별, 비어 있으면 기본 문구)로 답한다. 정상 입력을 막는 쪽이 더 나쁜 실패라 "ㅋㅋ", "응", "힘들어", 이모지 문장처럼 애매한 입력은 모두 LLM으로 보낸다. 걸러진 턴은 대화 기록에 `llm_skipped`로 남겨 비용을 추적한다. 체크인 프롬프트에는 "요약은 첫 답변에서만", "주제를 벗어난 작업은 하지 않고 캐릭터를 유지한 채 체크인으로 돌아온다" 규칙을 두고 이전 대화를 함께 넘긴다.
- **페르소나별 대화 유지:** (사용자, 페르소나, 체크인, 날짜)로 오늘 대화를 불러와 이어 간다. 탭을 옮기거나 페르소나를 바꿨다 돌아와도, 새로고침해도 유지되고, 날짜가 바뀌면 새 대화가 된다. [새 대화]는 이전 기록을 지우지 않는다.

### FR-10. 규칙성 기반 포인트 (게이미피케이션)

이벤트 점수 = 중요도 가중치 × 완료 여부, 연속 달성 streak 보너스(3일 ×1.1, 7일 ×1.25, 14일 ×1.5). (v2에서 확정 초안, 변경 없음)

### FR-11. 한국어/영어 다국어 지원 (v3 신규)

June의 요구: "앱은 먼저 한/영 사이에서 사용할 수 있게" — 즉 서비스 시작 시점부터 한국어·영어 두 언어를 모두 지원한다.

- `User.preferred_language` (`ko` / `en`) 필드로 사용자별 선호 언어를 저장.
- **클라이언트 UI:** Flutter의 표준 i18n 패키지(`intl`, `easy_localization` 등)로 모든 고정 문자열(메뉴, 버튼, 카테고리 라벨 등)을 리소스화.
- **페르소나 대화(FR-9):** 위 예시처럼 `sample_lines` 등을 언어별로 분리 저장, LLM 프롬프트에 응답 언어 명시.
- **알림 텍스트(FR-4, FR-4-1):** 푸시/텔레그램 알림 문구도 언어별 템플릿으로 관리.
- **FR-6 카테고리 라벨:** `overslept` 같은 코드값은 그대로 두고, 화면에 노출되는 라벨만 `{ "ko": "늦잠/기상 실패", "en": "Overslept" }` 식으로 이중 저장.
- (참고) LLM에게 자유 텍스트를 분석시키는 경우(FR-6의 `other`, FR-8 체크인 등) 입력 언어를 자동 감지하거나 `preferred_language`를 참고해 같은 언어로 응답하도록 지시.
- **✅ 화면 언어 전환 (2026-10-01):** 웹 화면은 처음 방문하면 영어이고, 오른쪽 위 [Eng | Kor]로 바꾼다(브라우저에 기억). 바꾸면 `PUT /users/me/language`로 `preferred_language`도 같이 바꿔 서버가 만드는 고정 문구가 같은 언어로 나온다.
- **✅ 대화 답변 언어 규칙 (어시스턴트·페르소나 공통):** 답변은 사용자가 **마지막으로 입력한 메시지의 언어**를 따른다. "ok", "좋아", 이름·숫자만 있는 입력처럼 판단이 애매하면 화면 언어(`preferred_language`)를 따른다. 한 답변 안에서 언어를 섞지 않는다. 확인 카드·경고·버튼·알림 같은 **고정 문구는 항상 화면 언어**다. (판단은 백엔드 `reply_language()`가 하고, 결과를 프롬프트에 넣는다.)

## 9. LLM 인퍼런스 비용 최적화 전략 (v3 신규)

기존 설계에 이미 반영돼 있던 "슬롯 상태만 전달", "구조화된 흐름 제한" 같은 기본기에 더해, 다음 4가지를 확정 반영한다.

1. **프롬프트 캐싱** — 페르소나 설정(FR-9)과 중요 기간 목록처럼 자주 바뀌지 않는 컨텍스트를 API의 프롬프트 캐시에 고정 배치해 입력 토큰 비용을 절감.
2. **LLM 우회 UI 숏컷** — FR-6에서 카테고리 버튼 선택만으로 끝나는 경우 LLM을 호출하지 않고 DB에 직행, `other` 선택 또는 자유 텍스트 입력 시에만 LLM 호출.
3. **하이브리드 라우팅 (장기 전략)** — 일정 어시스턴트(FR-2)는 로컬 sLLM, 페르소나 대화(FR-9)는 저비용 API로 분리하는 구조를 장기 목표로 두되, **MVP 단계에서는 인프라 부담을 피하기 위해 API로만 통일**하고, 트래픽이 늘어난 뒤 전환을 재검토한다 (열린 질문 #6).
4. **이벤트 상태 기반 컨텍스트 동적 로딩** — FR-8 일일 체크인 시, 완료된 이벤트는 개수만 요약하고 미완료 이벤트만 상세 정보(사유 포함)를 프롬프트에 주입.
